1. Qué es FerreStock en una frase

Es un sistema web de inventario para una ferretería. Registra productos, clientes y proveedores, compras, ventas con pago en efectivo, devoluciones y ajustes. Lleva el kardex y el costo promedio ponderado (CPP) y emite comprobantes simulados. Tiene dos roles: Administrador (todo) y Operativo (vende, compra y devuelve, pero no ve costos, ajustes, usuarios ni auditoría).

5. Backend: cómo está organizado

  • Paquetes por módulo (com.ferrestock.<modulo>): autenticacion, usuarios, catalogo, terceros, inventario, ajustes, compras, ventas, devoluciones, comprobantes, auditoria y monitoreo, más compartido (errores, montos, seguridad) y configuracion.
  • Capas: Controller (HTTP y permisos con @PreAuthorize) → Service (reglas de negocio y transacciones) → Repository (JPA). Los DTO de entrada se validan con anotaciones (@NotBlank, @Digits…) y mensajes traducidos.
  • Errores: siempre con el mismo formato (ProblemDetail, RFC 9457): codigo estable (por ejemplo EXISTENCIAS_INSUFICIENTES), mensaje en el idioma del usuario y errores por campo, que el formulario muestra junto al campo. Un error inesperado devuelve 500 con un código de correlación y queda registrado.
  • Montos exactos: BigDecimal con cantidades a 3 decimales, costos a 4 y dinero a 2 (HALF_UP). Viajan como texto en el JSON para no perder precisión.
  • Encabezado en todos los archivos (nombre, descripción, fechas, autores, versión); scripts/verificar_encabezados.sh lo revisa en el CI.

El corazón: inventario, costo promedio y concurrencia

  • MovimientoInventarioServicio es el único que cambia existencias y CPP. Cada compra, venta, devolución, ajuste o anulación deja un movimiento en el kardex (con el saldo y el CPP resultantes). La base de datos impide editar o borrar el kardex con un trigger.
  • CPP = (existencias × CPP actual + cantidad × costo de entrada) / (existencias + cantidad). Ejemplo: 10 a 1.000 + 30 a 1.400 = 40 unidades a 1.300. Las salidas salen al CPP vigente.
  • Nunca existencias negativas, ni con dos cajas vendiendo a la vez: los productos se bloquean (SELECT … FOR UPDATE) en orden de id dentro de la transacción. Además hay un CHECK (existencias >= 0) en la base. Probado: 2 ventas simultáneas de la última unidad confirman exactamente 1.
  • Consecutivos (VEN-000001, COM-, DEV-, AJU-) en una tabla con bloqueo de fila: no se repiten y no dejan huecos.
  • Anulaciones (solo ADMIN, con motivo): un documento no se borra, se anula con un movimiento compensatorio. Una compra no se anula si ya se vendió lo comprado o hubo entradas después; una venta no se anula si tiene devoluciones.

6. Frontend: cómo está organizado

  • src/modulos/<modulo>/ con servicios (llamadas a la API), paginas, componentes y validacion (esquemas Yup).
  • src/compartido/: tabla paginada (tarjetas en móvil), campos de formulario, editor de líneas de documentos, diálogos de confirmación y anulación, formatos de COP y fechas.
  • Rutas protegidas por sesión y rol; cada pantalla se carga solo cuando se visita.
  • Sesión persistente: al recargar, la app consulta /auth/sesion y restaura el usuario.
  • Validación doble: Yup en el navegador (respuesta inmediata) y Bean Validation en el servidor (seguridad). Los errores del servidor llegan al campo correcto.
  • i18n: español e inglés, 14 namespaces; un script verifica que no falte ninguna traducción.
  • Accesibilidad: axe-core en las E2E (WCAG A/AA), foco al primer error, etiquetas, contraste y navegación con teclado.
  • Tokens de diseño y tema claro/oscuro; JSDoc en cada archivo.

7. Base de datos

  • 14 tablas: usuario, categoria, producto, tercero, compra(+linea), venta(+linea), devolucion(+linea), ajuste, movimiento_inventario (kardex), consecutivo, auditoria, registro_error y persistent_logins.
  • Las reglas también viven en la base: CHECK (existencias ≥ 0, cambio = recibido − total, motivo obligatorio si está anulada), UNIQUE (código de producto, documento del tercero, un producto por línea), claves foráneas y triggers de inmutabilidad.
  • Hibernate solo valida el esquema (ddl-auto=validate); el esquema lo crean los scripts SQL. En local: db/crear_bd.sh. En la nube: db/inicializar_remota.sh (así se inicializó Neon).

9. CI/CD y Taiga

push o pull request a develop / main  ─►  GitHub Actions
  ├─ backend:  encabezados → unitarias + integración (PostgreSQL) → cobertura
  │            en main además: mutación → imagen Docker → despliegue → salud
  ├─ frontend: lint → i18n → build → Playwright (3 navegadores)
  │            en main además: despliegue → Selenium en Edge
  └─ reportar (siempre):
       ¿falló algo? ─ sí ─► issue + tarea en Taiga para el autor del commit (aviso por correo)
                    └ no ─► cierra el issue abierto de esa etapa, si lo había
  • Despliega solo si todo pasa: Render tiene el auto-deploy apagado. El job desplegar llama al deploy hook de Render cuando todas las etapas anteriores están en verde; sin hook, se despliega con Manual Deploy en Render.
  • Taiga: scripts/ci/taiga_reportar.sh se autentica con los secretos TAIGA_USUARIO y TAIGA_CLAVE de GitHub. No duplica issues: si ya hay uno abierto, lo comenta. Mapeo GitHub → Taiga en .taiga/miembros.json (Ananagl, JuanDav-L, mariam7799). Evidencia: issue #85 creado y cerrado automáticamente.
  • Backlog: scripts/taiga/cargar_backlog.py creó 14 historias (una por módulo de requisitos) y 70 tareas (una por requisito).
  • Scripts del repositorio: nueva_rama.sh, integrar.sh, liberar.sh (crea la etiqueta vX.Y.Z) y compilar_y_probar.sh. Versión actual en producción: v1.0.2.
  • El CI sí encontró errores reales: el nombre de la imagen de Docker debía ir en minúsculas, y en móvil faltaba que la tabla del comprobante fuera accesible con teclado. Ambos se corrigieron en la v1.0.2.

10. Métricas y monitoreo

  • Del equipo (scripts/metricas/metricas_taiga.py, lee el Taiga real): avance del tablero (hoy 93 %), tareas e issues abiertos y cerrados por integrante, horas promedio de resolución, fallos de CI y errores de producción.
  • De la aplicación: cada error 500 queda en registro_error con su correlación. Si el mismo error ocurre 5 veces en 10 minutos en la misma ruta, el backend crea solo un issue "[Producción]" en Taiga. El ADMIN consulta /api/v1/monitoreo/errores y /monitoreo/metricas (ventas del día, anulaciones, productos sin existencias, valor del inventario, errores y accesos denegados).

12. Guion sugerido para la demo (10 minutos)

  1. Abrir el sistema (1 minuto antes, por el plan gratis) → entrar como admin → cambiar de idioma y de tema.
  2. Ajuste de inventario inicial (20 a $400) → compra (10 a $550) → mostrar el kardex con CPP $450.
  3. Venta de 5 pagando $10.000 → cambio → comprobante con la leyenda de documento simulado → devolución de 2 desde la venta.
  4. Entrar como operativo: no ve costos ni ajustes; si escribe la URL de auditoría ve "Acceso denegado".
  5. Auditoría filtrada por usuario → GitHub Actions (pipeline en verde) → Taiga (issue #85 cerrado, tablero al 93 %).
Preguntas probables: "¿qué pasa si dos venden la última unidad a la vez?" → bloqueo FOR UPDATE + CHECK; probado con hilos reales. · "¿por qué no se borran documentos?" → trazabilidad: se anulan con movimiento compensatorio. · "¿cómo se calcula el costo?" → CPP ponderado con BigDecimal (ejemplo 1.300). · "¿qué pasa cuando falla una prueba?" → no se despliega y se crea un issue en Taiga asignado al autor del commit.
